# 運用失敗時の通知ルール

## 目的

Pulseeeの定期運用で失敗が発生したときに、検知、通知、一次対応、復旧報告を迷わず行える状態にする。

このドキュメントでは、Render Cron Jobの失敗を運用失敗として扱い、Slackの `#pulseee_ops` へ通知する運用を定義する。

## 対象

対象はRender上で運用している以下の3つのJobとする。

| Job名 | 主な役割 | 失敗時の影響 |
| --- | --- | --- |
| 未回答者リマインド（木曜日18:00） | 未回答者へのSlackリマインド送信 | 未回答者へのリマインドが送信されない |
| サーベイ自動作成 | 今週分サーベイの作成 | 今週分のPulseeeが作成されない |
| `pulseee-database-backup` | 本番DBバックアップ取得 | 最新のDBバックアップが保存されない |

## 検知方法

Renderの通知設定で、Job失敗時にSlackの `#pulseee_ops` へ通知する。

- 通知先: `#pulseee_ops`
- 通知種別: Only failure notifications
- 対象: 上記3つのRender Cron Job

Renderの通知を受け取った人は、該当Jobのログを確認し、このドキュメントの一次対応に沿って対応する。

## 共通対応フロー

1. `#pulseee_ops` に届いたRender失敗通知を確認する。
2. Render Dashboardで該当JobのRunログを確認する。
3. `#pulseee_ops` に一次報告を投稿する。
4. Job別の一次対応を実施する。
5. 復旧または暫定対応が完了したら、復旧報告を投稿する。
6. 同じ失敗が繰り返す場合は、原因調査用のIssueまたはタスクを作成する。

## 一次報告テンプレート

```text
【Pulseee運用失敗】
対象Job: <Job名>
発生時刻: YYYY/MM/DD HH:MM
影響: <想定される影響>
一次対応: <これから実施する対応>
Render URL: <該当JobまたはRunログのURL>
対応者: @名前
```

## Job別の一次対応

### 未回答者リマインド（木曜日18:00）

影響:

- 未回答者へのSlackリマインドが自動送信されていない可能性がある。
- 回答依頼自体は既に行われているため、サーベイ回答機能への直接影響はない。

確認:

1. RenderのRunログでエラー内容を確認する。
2. Slack上で未回答者リマインドが投稿済みか確認する。
3. 管理画面のサーベイ運用ページで、有効なサーベイと未回答者数を確認する。

一次対応:

1. 管理画面の「サーベイ運用」を開く。
2. Slack設定が設定済みであることを確認する。
3. 「Slack通知ジョブを登録」を実行する。
4. `#pulseee_ops` に対応結果を投稿する。

手動投稿で代替する場合:

```text
@channel Pulseeeの回答をお願いします！
https://pulseee-oknn.onrender.com/
```

### サーベイ自動作成

影響:

- 今週分のPulseeeが作成されていない可能性がある。
- サーベイが未作成の場合、対象者に回答画面が表示されない。

確認:

1. RenderのRunログでエラー内容を確認する。
2. 管理画面のサーベイ運用ページで「今週分サーベイ」が作成済みか確認する。
3. 作成済みの場合は、二重作成しない。

一次対応:

1. 管理画面の「サーベイ運用」を開く。
2. 「サーベイ作成ジョブを登録」を実行する。
3. 今週分サーベイが作成済みになったことを確認する。
4. 必要に応じて、`#pulseee_ops` に回答依頼の再確認を依頼する。

### `pulseee-database-backup`

影響:

- 最新のDBバックアップがS3へ保存されていない可能性がある。
- アプリの通常利用には直接影響しないが、障害時の復旧可能時点が古くなる。

確認:

1. RenderのRunログでエラー内容を確認する。
2. S3のバックアップ保存先に最新ファイルがあるか確認する。
3. `DATABASE_URL`、S3関連環境変数、AWS権限のエラー有無を確認する。

一次対応:

1. Render Dashboardから `pulseee-database-backup` を手動実行する。
2. 再実行後、S3にバックアップファイルが作成されたことを確認する。
3. 再実行も失敗する場合は、DBバックアップ・リストア運用設計を参照して原因を切り分ける。

関連ドキュメント:

- [DBバックアップ・リストア運用設計](backup_restore.md)

## 復旧報告テンプレート

```text
【Pulseee運用復旧】
対象Job: <Job名>
対応内容: <実施した対応>
結果: <復旧済み / 暫定対応済み / 継続調査>
影響範囲: <利用者影響やデータ影響>
次回対応: <必要なら記載>
対応者: @名前
```

## エスカレーション条件

以下に該当する場合は、`#pulseee_ops` で対応者を明示し、必要に応じて管理者へエスカレーションする。

- 同じJobが2回連続で失敗した。
- サーベイ自動作成が失敗し、管理画面からの手動作成も失敗した。
- 未回答者リマインドが失敗し、管理画面からのSlack通知も失敗した。
- DBバックアップが2日連続で失敗した。
- DBバックアップ失敗の原因が認証情報、S3権限、DB接続障害のいずれかである。
- 利用者から「回答画面が表示されない」「回答できない」と問い合わせが来ている。

## 運用メモ

- `#社内_バイト含む` は回答依頼など利用者向け通知に使う。
- Render Job失敗の通知や対応状況は、運用者向けの `#pulseee_ops` に集約する。
- 成功通知は原則流さず、失敗通知のみを扱う。
- Render Cronの時刻はUTCで設定されるため、通知・報告ではJSTの時刻を併記する。
